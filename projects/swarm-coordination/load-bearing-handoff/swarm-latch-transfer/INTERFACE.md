## Replacement data and provenance

A JSON object has `initial` (nonempty state string), `transitions` and `worlds` arrays. Each transition has `state`, `symbol`, `next` (nonempty strings) and integer `demand` in 0..4. Each (state,symbol) pair occurs once. Each world has `id` (unique nonempty string), `partial` and `lost` (booleans), `symbols` (six local input strings, one at the start of each half-slot), and `provenance` (nonempty text stating where those local symbols come from and how the joint relation was produced). Multiple worlds at a latch/report pair are allowed; none of the four pairs may disappear. Start the same D machine in the same initial state on all worlds. The next state and demand use only its state and the current local symbol. An input word or source variable can be shared across worlds; full runs need not be independent. A proposed correlation must be generated by a declared source-level shared condition, not by feeding hidden latch/report outcomes or borrowed future evidence into D's symbols. The checker validates deterministic local execution and the supplied finite relation; it cannot prove the declared provenance or completeness of a new scenario generator. Inspect that separately.

Restriction by each u gives a conditional row, which the checker reassembles using that exact u mass and checks against q. Coefficient and body data are singleton/trivial and add no verification obligation. Test every positive tuple. Do not replace the joint relation with a product of marginal demand profiles.
