Persistent decomposition discovery proof sources

This package contains proofs and reproducible finite checks for deciding when a
component found in partial descriptions remains an exact component of the full
system. It covers actual transition records, composition, time refinement, and
the extra conditions needed for causal implementation and control. Small
counterexamples show why successful local or coarse-time descriptions alone
are not enough.

The statements concern their explicitly declared finite models and bounded
search classes. The scripts support the written proofs; they are not formal
proof verification, empirical validation, or evidence of historical novelty.

Reading guide

1. theory/Exact_Dynamic_Factorization.md
   The main definitions and proofs: event factorization, reflection of hidden
   interactions, witness-preserving interface changes, path and spatial
   compatibility, quantitative view adequacy, and bounded discovery.

2. control/Causal_Implementation_and_Control_Transfer.md
   Staged causal implementation, enabled-action conditions, control transfer,
   finite-memory checking, and the boundary between semantic and physical
   realizability.

3. examples/Temporal_Cycle_Decomposition_Discovery.md
   A four-state obstruction and its permutation-cycle family. A coarse-time
   factor need not exist at the primitive time scale. The note also describes
   permitted signal and memory-based repairs.

4. examples/Docking_Cut_and_Control_Resource_Family.md
   Exact subsystem-boundary discovery and the raw sensing resource tradeoff in
   a finite adversarial docking family.

5. examples/Three_State_Circulation_Obstruction.md
   A transition coupling missed by every separate proper state-view summary,
   together with the information recovered when actual records stay aligned.

Checks and results

Each author checker is next to its result JSON in theory/, control/, or examples/.
independent_checks/ contains two separately implemented checkers and their
result JSON files. PROVENANCE.txt explains their distinct coverage and limits.

To reproduce every check, extract the complete archive and run, from its root:


Python 3.9 or later is required. No additional packages or network access are
needed. The runner first verifies SHA256SUMS, deletes each reference result
before invoking its checker, then requires both the regenerated JSON values
and exact bytes to match. It also compares printed and saved results and
verifies the complete manifest again. The final output is a JSON summary.
Do not redirect that summary into this package directory, because an extra
file would intentionally fail the strict inventory check. To retain it, use:


The runner modifies only the six bundled JSON result files, replacing each
with identical regenerated bytes on success. Individual checkers can also be
run directly; they write their JSON result next to their own script. Assertions
must remain enabled when running a checker directly. The runner enforces this.

SHA256SUMS covers every archive member except SHA256SUMS itself.

Verification scope: use the standalone mathematical checks identified in the project VERIFICATION.md. The original archive replay is not a supported repository command. No fresh Lean replay is claimed.
