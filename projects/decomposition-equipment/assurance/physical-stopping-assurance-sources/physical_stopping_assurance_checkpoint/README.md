# Physical stopping assurance checkpoint

Read Physical stopping assurance results.txt first. The abstract states the positive
result and its limits. This is a synthetic physical-interface bridge with compiled
controller logic, not a validated robot or a deployable hardware safety certificate.

## Runtime and reproduction

Tested with Python 3.12.14, NumPy 2.3.5, and GCC 14.2.0. A C11 compiler accepting
-fsanitize=undefined is required for the C comparison. From this directory:

    bash examples/run_checks.sh
    python3 theory/checks/check_first_loss_transfer.py
    python3 review/check_exposure_transfer.py
    python3 review/check_contextual_support.py
    python3 review/check_physical_counterexamples.py

The main checks compile fresh host test executables. They do not connect to devices.
The C stdio main is a test harness; the bounded supervisor/executor functions are the
implementation under review. Hardware drivers, clock accuracy, physical brake response,
and worst-case execution time are engineering premises, not established by host tests.

The simulator's collision field means conservative stopping-envelope violation.
It does not assert exact collision for every trajectory in the envelope. Exact rational
continuous-kinematics checks separately verify the travel bound.

Timing: 100 ms after the scheduled ramp endpoint is a nominal sample checkpoint;
310 ms is hard watchdog expiry eligibility; physical engagement is bounded by 320 ms.
The extra 10 ms is ONE shared budget across sample/ACK/watchdog dispatch and mechanical
engagement, in addition to nominal computation. It is not 10 ms separately per stage.
These bounds remain unvalidated physical assumptions.

The principal all-support case is conditional on exact learned response, the stipulated
residual support, source/physical action compatibility, and the physical envelope.
It does not pay empirical-source probability error when every structural outcome is safe.
The illustrative approximately 9.17 percent probabilistic bound is not a field-safety target.

No new training records were collected for this milestone. The released n12 predictor
and its original records/certificates are included under references/predictive_checkpoint.
The current examples/inputs/executable_candidate.json is the identical frozen candidate.
To recheck the old n12 data and source sampling:

    python3 references/predictive_checkpoint/examples/check_saved_artifacts.py references/predictive_checkpoint/examples/runs/n12
    python3 references/predictive_checkpoint/examples/check_exact_source_sampler.py references/predictive_checkpoint/examples/runs/n12

NumPy is needed for those inherited checks. The new physical/timing and C checks use
Python's standard library and the C compiler. The earlier generic proof is included to
state exactly what its statistical guarantee requires. Older source-relative references
in that proof refer to the earlier complete checkpoint, not newly implemented algorithms.

The favorable input history is supplied and observed. Its safe physical induction is not
proved. The speed comparison is within a specified motion protocol/grid, not global
controller optimality, throughput, or successful arbitrary navigation.
